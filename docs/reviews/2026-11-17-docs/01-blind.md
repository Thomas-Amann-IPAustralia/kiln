## What would worry an expert

### 1. High — Recording authority is not the same as enforcing it

**Where:** `docs/sketches/phase-0-shared-core.md`, “Contracts others will depend on” and slices 1–2; `docs/charter/agents/coding-swarm.md`, “How a loop runs”; `docs/decisions.md`, D-005 R3.

The live swarm instructions still let a loop set its own `passes` flag. D-005 correctly identifies this problem, but the independent verifier remains an unadopted recommendation. Similarly, an approval record containing `actor: tom` does not establish that Tom authorised it.

**Why it matters:** An agent could accidentally certify its own work or misattribute approval, while producing perfectly valid records.

**Change:** Adopt R3 before building the loop. Specify permissions enforced outside the coding agent: protected verification rules, a separate verification process, and a human-only approval path tied to the exact version being approved.

### 2. High — Phase 0’s safety promise exceeds its proposed checks

**Where:** `docs/charter/build-plan.md`, phase 0 and “First moves” item 7; `docs/sketches/phase-0-shared-core.md`, slices 3–6 and the paragraph deferring other components.

The charter promises harness controls before agents receive tools. However, the sketch postpones the capability broker—the component controlling credentials—and omits the promised Semgrep, OSV-Scanner and Trivy baseline. Its sandbox demonstration proves a program runs under a cap and cannot reach one forbidden host; that does not establish the wider safety boundary.

**Why it matters:** These omissions matter once unattended code can run, not merely before production.

**Change:** Reconcile the checklist before approval. Require tests showing that forbidden file, network and credential access is refused, and spending is refused *before* exceeding a cap. A small, restricted runner may suffice initially; a bespoke broker need not be built prematurely.

### 3. Medium — The rules disagree about when Tom must approve

**Where:** `docs/charter/operating-model.md`, “Rules every agent follows” rule 11, “Constraints, autonomy and escalation”, and “Tom’s role”; `docs/charter/agents/coding-swarm.md`, opening paragraph.

Rule 11 says, “Only a tripwire waits for Tom.” Elsewhere, Tom must approve four gates and any change to an approved plan. The swarm’s opening likewise mentions Red items and tripwires but omits the Tom band.

**Why it matters:** An agent following the shorter rule could continue through a change that should return to you.

**Change:** Use one consistent formulation: agents decide within delegated authority; they pause for tripwires, designated human approvals and changes to previously approved decisions. Correct the summaries as well as the detailed table.

### 4. Medium — Essential safety instructions are Claude-specific

**Where:** `AGENTS.md`, introduction and “Security”; `CLAUDE.md`, “How we work” and “When to stop and ask Tom”.

`AGENTS.md` is intended for every coding agent, but the explicit no-budget/no-paid-call rule, adoption rules and shared-infrastructure approval rules live in `CLAUDE.md`. Only Claude Code is guaranteed to receive both.

**Why it matters:** Switching to Codex, Cursor or another runner could change the agent’s effective authority without anyone intending it.

**Change:** Put a short universal authority-and-spending section in `AGENTS.md`. Keep Claude-specific behaviour in `CLAUDE.md`, and detailed procedures in linked documents. The issue is instruction placement, not the existence of many documents.

### 5. Medium — Too much infrastructure precedes the first useful result

**Where:** `docs/sketches/phase-0-shared-core.md`, “Build order”; `docs/charter/build-plan.md`, phases 0–2; `docs/charter/build-method.md`, “Vertical slices, not layers”.

Phase 0 proposes hosted storage, vector indexing, ingestion, orchestration and a sandbox before the first useful chair/Researcher run. Yet the method explicitly favours small, end-to-end slices. Seven expert responsibilities are defined, but there is no comparison showing when separate agents improve results.

**Why it matters:** You could spend several sessions making the factory internally complete before learning whether it produces useful work.

**Change:** Keep the non-negotiable safety controls, but make the first milestone one brief, one evidence-backed plan and one verified coding ticket. Before expanding beyond the first agents, compare that path with a simpler single-agent baseline on quality, cost and elapsed time. Do not assume either design wins.

### 6. Medium — The inherited evaluation method contradicts itself

**Where:** `docs/repo-seeds/sop-agent-construction-v3.md`, §12 and §20.5; `CLAUDE.md`, “How we know”.

The SOP correctly says “choose on dev, report on test”: use development cases to choose settings, then untouched cases for the final assessment. But §20.5 evaluates candidate models on the **test split** to choose the model.

**Why it matters:** Repeatedly choosing against the final exam makes its eventual score less trustworthy.

**Change:** Write a short live evaluation policy resolving this contradiction. Choose models and settings on development cases; reserve untouched cases for confirmation. Retain difficult failure cases separately. Do not edit the sealed SOP.

### 7. Medium — One privacy guarantee is too strong

**Where:** `docs/repo-seeds/sop-agent-construction-v3.md`, §23, “API clients are pinned”.

The SOP says `store=false` means “the provider keeps no copy”. That flag alone does not establish zero retention. Retention for abuse monitoring, endpoint-specific storage and contractual data controls require separate checking.

**Why it matters:** Government-facing work must not rely on a stronger privacy promise than the provider actually makes—even if current builds exclude real personal information.

**Change:** Add a correction in the live security guidance. Record the verified retention conditions for each provider and endpoint before use; do not equate one request flag with zero retention.

## What is good practice and should be kept

- **Explicit scope and honest status.** Built, proposed and deferred work are distinguished clearly. Keep this discipline. — `CLAUDE.md`, “Current scope”; phase 0 sketch, status.
- **Deterministic checks before model judgement.** Typed inputs, strict configuration, offline tests and atomic writes are sensible foundations. — `AGENTS.md`, “The quality bar” and “Conventions”.
- **Reproducible evidence and spending controls.** Versioned prompts, cached paid responses, run manifests and pre-agreed budgets make mistakes inspectable. — SOP §§13–14 and §20.
- **Small-scale execution before parallel swarms.** One sequential loop first is a sound starting point. — `docs/charter/agents/coding-swarm.md`, “Limits”.
- **Independent challenge without endless debate.** A fresh, cross-provider review with owner responses and recorded dissent is useful; it remains something to measure, not a guarantee of correctness. — `docs/charter/operating-model.md`, “Adversarial review before G2”.

## Deferring the Interpreter

**Defer the autonomous Interpreter agent, but not the human interface.**

A separate model that explains, questions and routes adds another place where meaning can change. Its intended boundary—explaining decisions without making domain decisions—is sensible. Building it after the underlying records and workflows stabilise reduces rework. — `docs/charter/agents/interface-agents.md`, “Interpreter”.

However, phase 5 is too late to discover whether you can understand and control Kiln. The documents identify your attention as scarce, yet the current handover contains **13 items for Tom**. That is a reason to test the interaction early, not necessarily to build another agent. — `CLAUDE.md`, “How we work”; `docs/handover.md`, “For Tom”.

**Build earlier, alongside slices 1–2:**

- A short, plain-English intake and status view.
- One decision format showing the recommendation, consequences, dissent and exactly what needs your answer.
- An approval mechanism showing which version you are approving.
- A clear distinction between “recorded”, “recommended” and “approved”.

The existing proposed approval command is a start. — Phase 0 sketch, slice 1; operating model, “Tom’s role”.

**Defer the Illustrator agent too.** Add simple diagrams earlier only where they help you understand a real decision, preferably rendered directly from structured records. That matches its existing “adds no content” boundary. — `interface-agents.md`, “Illustrator”.
