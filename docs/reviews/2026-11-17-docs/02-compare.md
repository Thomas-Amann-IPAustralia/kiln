**2. Should documentation stop until code exists?**  
D-006’s “No new design document” recommendation is too categorical. The blind review is right to require repairs to the existing sketch before implementation. Code and tests cannot alone specify intended authority or obligations: they can faithfully implement the wrong policy. This needs a targeted revision, not another planning document.  
*Sources: D-006, finding 3; blind, findings 1–2 and 5; `docs/sketches/phase-0-shared-core.md`, “Build order”.*

**3. Should enforced rules disappear from instructions?**

Keep short statements of important boundaries, with detailed procedures elsewhere. The blind review’s proposed universal authority section is better.  
*Sources: D-006, finding 2; blind, finding 4.*

## The CODEOWNERS correction

**Yes, given the account setup D-006 reports.** If Tom is the sole applicable code owner and also the pull-request author, he cannot supply the required approval himself. Normal merges would be blocked; an authorised bypass might still allow them. “Every merge” is therefore shorthand, not literally every possible merge.  
*Source: D-006, “A correction (D-001)”.*

Its replacement is sensible **for one person using one GitHub identity**:
- Require a pull request.
- Require every intended CI job, including the separate secret-scanning job.
- Do not require an approval nobody eligible can provide.

But this enforces workflow, **not human review**. If Claude can merge or bypass protections using Tom’s credentials, GitHub cannot distinguish Claude from Tom. Reserve merging for Tom through restricted agent permissions; use a separate agent identity if enforceable separation becomes necessary.

Also, D-001’s statement that CODEOWNERS “routes changes” was not wholly wrong: requesting reviews is routing. The mistake was treating that as enforceable approval.  
*Sources: D-006, correction; `docs/decisions.md`, D-001, CI and CODEOWNERS bullets.*

## The Interpreter

D-006’s proposals make the blind review’s advice practical:

1. **Decision card: adopt.** An ID and hash identify exact card contents, but referenced plans and contracts must also be pinned to versions. Neither hashing nor an `actor` field proves Tom approved anything.  
   *Sources: D-006, proposal 1; blind, finding 1.*

2. **Mermaid diagrams: use where helpful.** Keeping diagram source as text reduces export loss; it does not establish correctness. Preserve links to underlying records.  
   *Sources: D-006, proposal 2; `docs/charter/agents/interface-agents.md`, “Illustrator”.*

3. **Friction log: adopt lightly.** Record confusing wording, clarification and outcome—not another elaborate reporting process. This supplies real interaction examples for later evaluation.  
   *Sources: D-006, proposal 3; blind, “Deferring the Interpreter”.*

One qualification: the eventual Interpreter cannot be **only** a renderer. Its charter also requires questioning Tom and explaining unfamiliar material. Rendering approvals should be constrained; conversation needs separate testing.  
*Source: `docs/charter/agents/interface-agents.md`, “Interpreter”.*
